状态：第一期已实现（`mytest/plugins/trpg_plugin/`），还没有用真模型跑过完整一局。实现和设计不一样的地方见第 12 节。部署和试玩见第 13 节。

## 0. 已经定下的

| 项目 | 决定 |
|---|---|
| 谁来驱动 | NoneBot 新插件 `trpg_plugin`。凛音只做 KP，不带平时聊天的记忆，不受好感度影响 |
| 节奏 | 异步团，1–5 人 |
| 规则 | CoC 7 版，不限恐怖题材 |
| 掷骰 | 代码自动掷；需要玩家选择的（孤注一掷、花幸运）等玩家回答 |
| 意图和判定 | AI 判断要不要检定、检定什么、多难；成败只看代码掷的骰 |
| MaiBot | 跑团用新建的群，整个群 MaiBot 都不说话 |
| 场外 | 括号括起来；括号里以「KP」开头的是场外提问，凛音只读状态、照实回答；忘了加括号，回复那条消息说「场外」 |
| 一轮怎么结束 | 所有在场的人都行动了就结算；有人没动时凛音问「还有人要行动吗」，再没回应就当原地待命 |
| 中途加入 / 离开 | 下一轮叙述里编一个简短的来由 / 退因，不出戏 |
| 开团 | 群员都能开；暂停和结束只有开团人、群管理员、superuser |
| 即兴 | 可以编保持真实感的细节（路人、天气、陈设），不编线索和剧情事实 |
| 越权声明 | 温和处理：当成尝试，在剧情里自然落空或引出反应，不说教 |
| 口吻 | 混合：旁白中立描述场景；询问行动、宣布检定、场外提醒由凛音以主持人身份说 |
| 模型 | 每个环节可配主模型；三次没有有效回复就换下一个，可以换服务商 |
| 调查员 | 模组预设角色，或从 `.st` 角色卡导入 |
| 卡关提示 | 连续几轮没进展时凛音提出灵感检定，过了给一条模组写好的提示 |
| 第二期 | 战斗、车卡、私聊线索、AI 把模组原文转成结构化格式 |

## 1. 和现有系统的关系

```
跑团群 ──NapCat──┬── NoneBot：trpg_plugin（KP 的全部逻辑）
                 └── MaiBot：rinne_trpg_guard 插件，跑团群里拦掉所有消息，MaiBot 不回复
```

- **MaiBot 静默**：新写一个 MaiBot 插件 `rinne_trpg_guard`。
  - 用 `EventHandler(event_type=ON_MESSAGE_PRE_PROCESS, intercept_message=True)` 拦截跑团群的消息。
  - 跑团群名单由插件配置填写。
  - **待验证**：SDK 里拦截后具体返回什么、MaiBot 实际会不会停止处理，本机验证不了。开工第一步在服务器上验证。
  - 兜底方案：用 `frequency.set_adjust` 把这个群的回复频率调到最低，或在 MaiBot 的 `ban_msgs_regex` 之外按群屏蔽。
- **NoneBot 内部**：
  - 复用 `dice_girl_plugin/dice/coc.py`（检定、奖励骰 / 惩罚骰、理智）和 `expression.py`。
  - 复用 `_shared/services/llm.py` 的调用和错误处理，扩展成多模型兜底。
  - 复用 WebUI 的配置注册表和列表管理卡片，复用运行状态页。
  - 跑团群里，骰娘的 `.ra / .sc / .st` 照常可用，但团进行中改角色卡要经过 KP，见 §6。

## 2. 数据

一个 SQLite 文件 `data/trpg_plugin/trpg.db`。原则：所有事实存在数据库里，AI 每轮从这里读取，不靠它自己记。

### 2.1 模组（JSON 文件，导入时校验后存进数据库）

模组 ID 和所有内部 ID 用无含义的编号（`c1`、`n2`），防止 ID 本身泄密。

下面是最初的草稿。实际实现的格式见 `docs/trpg-module-format.md`，和草稿的区别：标记也用无含义编号（`f1`）；线索只在线索里写所在场景，场景不再列线索；去掉 `on_enter`，进场景触发的事件写成 `"when": {"scene": "s2"}`；顶层加了真相的 `spoiler_words`；线索可以 `set_flags`。

```jsonc
{
  "format": 1,
  "id": "m_tea_house",
  "title": "茶馆失物",
  "tone": "日常悬疑",                  // 叙述基调
  "era": "现代，南方小城",
  "players": [1, 5],
  "intro": "给玩家看的开场……",
  "truth": "只有 KP 知道的真相……",      // 只给裁决环节
  "start_scene": "s1",
  "scenes": [{
    "id": "s1",
    "name": "茶馆大堂",
    "public": "玩家进来时能看到的描述",
    "hidden": "只有 KP 知道的：柜台后面的暗格……",
    "exits": [{"to": "s2", "how": "穿过后门", "requires": []}],
    "npcs": ["n1"],
    "clues": ["c1", "c2"],
    "on_enter": [],                    // 进入时触发的事件 id
    "hints": ["卡关时给的提示"]        // 灵感检定成功时按顺序给
  }],
  "clues": [{
    "id": "c1",
    "scene": "s1",
    "where": "柜台账本",                // 线索跟着具体的东西走
    "text": "揭示时给玩家的内容",
    "how": {"skill": "侦查", "difficulty": "regular"},   // 或 null：查对了地方直接给
    "key": true,                       // 推进剧情必须的
    "on_fail": "",                     // 失败也能得到 / 失败另有后果，大多数留空
    "spoiler_words": ["暗格", "账本被改"]   // 叙述里出现就说明漏了，用于剧透检查
  }],
  "npcs": [{
    "id": "n1",
    "name": "掌柜老周",
    "public": "外貌、身份，第一次见面能看到的",
    "personality": "性格、说话方式",
    "knows": ["他知道且愿意说的"],
    "secrets": ["他知道但会隐瞒的"],     // 只给裁决环节
    "lies": ["他会说的谎"],
    "attitude": "neutral",
    "social": {"说服": 50, "心理学": 40}, // 对他做社交检定时的难度依据
    "spoiler_words": []
  }],
  "events": [{
    "id": "e1",
    "when": {"flags_all": ["f_found_ledger"], "scene": "s2"},
    "public": "事件发生时玩家看到的",
    "sanity": {"success": "0", "fail": "1d3"},   // 理智损失由模组写死，AI 不写数字
    "set_flags": ["f_ghost_seen"]
  }],
  "flags": [{"id": "f_found_ledger", "desc": "找到了被改的账本"}],
  "endings": [{"id": "end1", "when": {"flags_all": ["f_truth"]}, "public": "结局叙述要点"}],
  "pregens": [{"name": "林晓", "occupation": "记者", "sheet": "侦查60 图书馆70 心理学40 理智55 …"}]
}
```

导入校验：所有引用的 id 都存在；每个场景至少能走到一个结局；关键线索都有能拿到的路径；没有 id 重复；`spoiler_words` 不为空的项目都在 `hidden / secrets / truth` 里有对应内容。

### 2.2 团的状态（表）

| 表 | 内容 |
|---|---|
| `campaign` | 群号、模组、阶段（招募 / 进行中 / 暂停 / 结束）、开团人、当前场景、游戏内时间、`revision`（每次状态改变 +1） |
| `campaign_player` | QQ 号、调查员名、角色卡（技能、HP、SAN、幸运、物品）、状态（在场 / 待命 / 离开）、加入轮次 |
| `campaign_flag` | 已设置的剧情标记 |
| `campaign_clue` | 已揭示的线索、是谁拿到的、第几轮 |
| `campaign_npc` | NPC 当前态度、是否登场、位置 |
| `campaign_fact` | 已确立的事实（NPC 说过的话、约定、谎言），带可见性：kp / public |
| `round` | 每一轮：编号、阶段（收集中 / 结算中 / 叙述中 / 完成 / 失败）、`revision`、各步骤的输入输出（JSON） |
| `round_action` | 本轮收到的行动：QQ 号、消息 ID、原文、是否被撤回（场外） |
| `round_roll` | 掷出的骰：谁、技能、难度、点数、结果、是否孤注一掷。写入后永不改 |
| `outbox` | 待发消息：内容、目标、状态（待发 / 已发 / 失败），发送失败重试，不重复发 |
| `log` | 全部收发和每次模型调用（模型、耗时、token、结果），带可见性 |
| `summary` | 剧情摘要：覆盖到第几轮、内容 |

角色卡在团里单独存一份（不直接改 `.st` 的那张），团结束时可以选择写回。

## 3. 每一轮的流程

参考 diceframe：先统一规划检定，代码掷骰，再按固定结果叙述。改掉它的两处：叙述看不到秘密；线索由代码校验后才发。

```
收集行动 → ①理解行动 → ②裁决 → ③代码校验 → ④掷骰并更新状态 → ⑤叙述 → ⑥叙述检查 → 发送
                                 ↑不合格把错误给模型重来        ↑不合格重写，骰子不重掷
```

| 步骤 | 谁做 | 能看到什么 | 输出 |
|---|---|---|---|
| 收集 | 代码 | — | 本轮每人的行动（同一人多条合并，撤回的去掉） |
| ①理解行动 | 模型 | 全部资料 | 每人的意图、方法、对谁说话、原话、越权部分、本轮之后的待办 |
| ②裁决 | 模型 | 全部资料 + 最近的检定 | 每人要不要检定（技能、难度、奖励 / 惩罚骰、理由）、成功 / 失败各得到哪些线索、设置哪些标记、移动到哪、耗时、孤注一掷的后果 |
| ③校验 | 代码 | — | 见下文。不合格就把错误原文给模型再裁一次 |
| ④掷骰 | 代码 | — | 写 `round_roll`，按结果应用线索、标记、移动、理智（数值来自模组） |
| ⑤叙述 | 模型 | **只有公开信息**：公开场景描述、已揭示线索、登场 NPC 的公开资料和本轮获准说的内容、本轮结果（结论，不给点数）、最近几轮公开记录、摘要 | 正文；凛音的主持人台词单独一段 |
| ⑥检查 | 代码 | — | 见下文 |

①和②可以合成一次调用（省时间），默认分开（更稳），WebUI 里可切换。

**③校验规则**（合法选项同时写进输出格式的枚举，从源头收窄）：
- 技能在这名调查员的角色卡上存在，或是 CoC 基础技能（按基础值算）。
- 线索属于当前场景，且未被揭示过；需要检定的线索，只能挂在「成功时」下。
- 移动目标是当前场景的出口，且出口的条件已满足。
- 标记在模组里定义过。
- 难度只能是 regular / hard / extreme；奖励 / 惩罚骰 -2..2。
- 同一个人、同一个对象、同一个技能、情况没变：不能再检定一次（重复检定）。
- 每人每轮最多一个主检定。
- 引用的 NPC 在当前场景登场。

**⑥叙述检查**：
- 正文里出现任何**未揭示**的线索、秘密、真相的 `spoiler_words` → 重写。
- 检定失败的人，正文里不能出现「成功」「侥幸」「居然」之类绕过失败的写法（规则 + 关键词）。
- 没登场的 NPC 不能开口。
- 篇幅超过上限 → 压缩一次。
- 可选（默认开）：再用一次模型专门审一遍「有没有透露没揭示的东西」。
- 重写最多 2 次，还不行就退回安全版本：只用代码拼出的结果说明（谁做了什么、检定结果、得到的线索原文）。

### 3.1 版本号和恢复
- 每轮开始时记下 `campaign.revision`。模型回复到达时版本号变了（有人撤回、超时、被管理员修改），这次回复直接丢弃。
- 每一步做完就写进 `round`，机器人重启后从断开的那一步继续。
- ④之后才失败的，只重做⑤⑥，骰子不重掷。④之前失败的，整轮回到「收集完成」，下次重来。

## 4. 模型调用和失败处理

- WebUI 新分区「跑团」，里面配：裁决模型、叙述模型、审查模型，以及一个**兜底模型列表**（每项填接口地址、密钥、模型名，可以是不同服务商）。
- 每次调用：
  1. 用当前模型请求，要求结构化输出（支持 JSON Schema 的接口用 schema，不支持的用 JSON 模式 + 解析）。
  2. 无效（超时、HTTP 错误、不是 JSON、校验不过、正文为空）算一次失败，最多 3 次；输出被截断时下一次加大 token 上限。
  3. 3 次都失败换兜底列表的下一个模型，同样最多 3 次。
  4. 全部失败：凛音发一句场外的话（「KP 去续杯了，稍等」），这一轮停在当前步骤，5 分钟后自动重试；也可以用 `/kp 重试`。
- 每次调用的模型、耗时、token、失败原因写进 `log`，在运行状态页显示。

## 5. 群里怎么玩

| 指令 | 谁能用 | 作用 |
|---|---|---|
| `/开团 模组名` | 群员 | 进入招募 |
| `/加入 [预设角色名]` | 群员 | 加入；不写就用自己 `.st` 的卡 |
| `/开始` | 开团人 | 开场 |
| `/暂停`、`/继续`、`/结束` | 开团人、群管理员、superuser | — |
| `/kp 状态` | 所有人 | 当前场景、在场的人、谁还没行动 |
| `/kp 重试` | 开团人、管理员 | 卡住时手动重试当前步骤 |
| `/离开` | 玩家 | 下一轮编一个退因 |

- 进行中的群里，玩家**不带前缀的普通发言**就是角色行动。
- `（……）` 或 `(……)` 括起来的是场外，凛音不处理；`（KP ……）` 是场外提问。
- 回复自己的某条消息说「场外」，那条就不算行动。只在本轮开始结算之前有效。
- 结算开始后再收到的行动，算下一轮的。
- 凛音每轮的回复分两段：旁白正文；凛音以主持人身份说的话（宣布检定结果、询问「还有人要行动吗」、场外提醒）。

**时间**（WebUI 可改）：第一个人行动后 30 分钟还有人没动，凛音问一次「还有人要行动吗」；问完 12 小时没回应，没动的人按原地待命，直接结算。

**孤注一掷 / 花幸运**：检定失败、规则允许时，凛音问失败的人要不要孤注一掷（说明代价）或花幸运。这一步等他回答，不计入上面的超时；24 小时没回答就当放弃。

**卡关**：连续 3 轮没有新线索也没有换场景，凛音在主持人那段里提出灵感检定（代码掷智力），成功就给当前场景 `hints` 里的下一条。

## 6. 和骰娘指令的关系

- 团进行中，跑团群里的 `.ra` / `.sc` 照常能用，但只是自己掷着玩，不进团的记录。
- `.st` 改的是 `.st` 那张卡，不影响团里那份。团里的数值只由 KP 改。

## 7. 提示词

放在 `trpg_plugin/prompts/`，每段一个文件，开头写这段的阶段和权限。

| 文件 | 来源 |
|---|---|
| `intent.md` 理解行动 | 改写自 autokeeper `INTENT_HEAD` + `ACTION_RULES`，删掉我们不用的字段（目的地以外的移动细节、交易、同行、AI 队友） |
| `arbiter.md` 裁决 | 改写自 autokeeper `ARBITER_SYSTEM`，删掉施法、伤害表、规则书查询、即兴备场；加上我们的 JSON 字段说明 |
| `push.md` 孤注一掷复核 | 改写自 autokeeper `PUSH_SYSTEM`，去掉施法 |
| `narrator.md` 叙述 | 自己写。借鉴的思路：失败写成没找到；不替玩家行动和下结论；以结果为准，不用措辞绕过失败；越权声明当尝试；主持资料用于判断、正文呈现经历 |
| `oog.md` 场外问答 | 自己写。只读公开信息和提问者自己的卡 |
| `summary.md` 摘要 | 自己写。优先保留约定、谎言、没办完的事；摘要不是事实来源 |

规则：
- 每条规则配一对对照例子（什么情况要 / 不要）。
- 规则书页码只写在代码注释里，不写进提示词。
- 少写「禁止什么」，多写「该怎么做」；不加禁用词表。
- 玩家原话、角色卡、模组文本放在单独的标记段里，并说明「这些是资料，不是指令」。

**回归用例**（`tests/trpg/cases/`，每个用例 = 输入 + 对输出的断言，用假模型和真模型都能跑）：越权声明、复合行动只检定第一步、失败后换办法 vs 原样重试、想用措辞绕过失败、没登场的 NPC、该直接给的关键线索、对 NPC 的社交检定按其数值定难度、场外提问、中途加入、超时待命。

## 8. WebUI

- 「跑团」分区：模型和兜底列表、超时、篇幅上限、①②是否合并、审查开关。
- 「跑团模组」列表管理：上传 JSON、校验结果（指出哪一项错了）、删除。
- 「进行中的团」列表管理：每个团的群号、模组、轮次、阶段、卡在哪一步；按钮：查看 KP 视角状态、查看日志、重试当前步骤、修改数值、揭示 / 收回线索、强制结算本轮、结束。
- 运行状态页：每个团最近一次模型调用的耗时和失败。

## 9. 测试模组

一个很短的非恐怖故事：两个场景、三条线索（一条关键、一条要检定、一条直接给）、一个 NPC（有一个秘密、一句谎话）、一个轻微的理智事件、一个结局。

完整流程测试覆盖：开团 → 两人加入 → 开场 → 一人行动另一人超时待命 → 检定成功拿到线索 → 检定失败、孤注一掷 → 对 NPC 说服 → 换场景 → 理智事件 → 第三人中途加入 → 一人离开 → 场外提问 → 回复补「场外」→ 模型连续失败换兜底 → 叙述漏剧透被拦下重写 → 重启后从中间恢复 → 结局。

## 10. 实现顺序

1. 在服务器上验证 MaiBot 能否在指定群静默（探测插件，只记录，不拦截 → 再试拦截）。**这一步不通过，后面先不做。**
2. 模组格式、导入校验、测试模组。
3. 数据表和团的状态机（招募、开始、暂停、结束、加入、离开）。
4. 行动收集、场外判断、超时。
5. 规则引擎补齐：难度等级、孤注一掷、幸运、灵感检定。
6. 模型调用层：结构化输出、重试、兜底列表、版本号。
7. ①②③④：理解行动、裁决、校验、掷骰和状态更新。
8. ⑤⑥：叙述、剧透检查、重写和安全版本。
9. 发送队列、重启恢复。
10. WebUI。
11. 回归用例和完整流程测试。

## 11. 还没定、实现中再确认的

- 叙述每段的字数上限：按建议实现（普通 120–260 字；换场景、结局 200–500 字；孤注一掷 / 花幸运之后 60–160 字）。超过上限 1.6 倍才要求压缩。
- 摘要：按建议实现（每换一个场景 + 每 10 轮）。
- 模型能力：还没确认，见第 13 节，用回归用例在服务器上跑一遍。

## 12. 实现和设计不一样的地方

- **开场白不用模型**：直接发模组的 `intro` 原文和第一个场景的公开描述，保证不漏、不编。
- **①和②固定分开调用**，没做「合并成一次」的开关；都用「裁决用的模型」。
- **第一期不分队**：有人走了出口，全队一起移动。
- **孤注一掷换技能**：复核模型说做法换了要用别的技能时，用新技能掷一次，同样算孤注一掷。
- **有没回答的孤注一掷 / 花幸运时**，下一轮照常收集行动但先不结算，回答完（或 24 小时当放弃）马上结算。设计里「不计入超时」就是这样实现的。
- **卡关提示**挑在场智力最高的人掷灵感；给过一次之后隔 3 轮才会再试。
- **WebUI**：模组和进行中的团放在「跑团」分区下的同一张列表里（按钮按类型生效）；「修改数值」只能改理智、幸运、HP。设计里「强制结算本轮」没做，可以用「马上重试」。
- **审查**（⑥ 的可选项）默认开。审查模型自己挂了当通过（关键词检查照样做）。
- **回归用例**放在 `trpg_plugin/regression_cases.json`（不在 `tests/trpg/cases/`），这样服务器上能直接用真模型跑。

## 13. 部署和试玩

1. 推送、在服务器上拉代码、`docker compose up -d --build` 重建 NoneBot。
2. WebUI「跑团」里：填跑团群 `1130489499`；模型留空就用「大模型」里的。测试时可以把「多久问一次还有人要行动吗」调成 1 分钟、「原地待命」调成 1 小时。
3. **先用真模型跑回归用例**，看提示词在你的模型上表现怎么样。在 docker-compose 文件所在的目录，先用 `docker compose ps` 看 NoneBot 的服务名，再执行（把「服务名」换掉）：
   ```bash
   docker compose exec 服务名 python scripts/trpg_regression.py
   ```
   它读的是 WebUI 里保存的模型配置，和真实游戏用同一套。
   每个用例显示 ✓ 或 ✗，✗ 的会附上模型的原始输出。把结果发回来，按结果改提示词。
   只跑某几个：在命令后面加用例名。
4. 在群里 `/开团 茶馆失物`，两三个人 `/加入 林晓`，`/开始`，按正常跑团的方式说行动。
5. 出了问题：WebUI「跑团」列表里点团的「最近日志」看每次模型调用和叙述检查的结果；「KP 视角」看线索和标记的真实状态。
